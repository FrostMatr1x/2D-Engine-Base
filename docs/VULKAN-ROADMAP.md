# 2D-Engine-Base → движок для симуляций (Vulkan)

Дата: 2026-10-10. Фокус смещён: **не игровой движок, а движок симуляций**. ImGui, UI, игровой слой — вне задачи.
Нужны только **отрисовка и объекты**.

Хост: Fedora 44, RTX 4060 (nvidia 615.71.09), Wayland + GNOME Classic.

---

## 1. Что меняется от смены фокуса

| | Игровой движок | Симуляция |
|---|---|---|
| Модель данных | `GameObject` + компоненты, объект = штука с поведением | **SoA**: массивы состояний, N = 10⁴…10⁷ |
| Шаг времени | переменный `dt`, «сколько успели» | **фиксированный `dt`**, детерминизм, шаг ≠ кадр |
| Отрисовка | спрайты, атлас, текст, UI | **точки, линии, инстансированные квады** |
| Текстуры | нужны почти сразу | **не нужны вообще** на первых этапах |
| Дескрипторы | атлас + sampler | не нужны, пока нет текстур (только push constants) |
| Что ценно | красивая картинка | **воспроизводимость и выгрузка данных** |
| Запуск | окно | окно **+ headless** (батч, ночь, параметрический свип) |
| Инструменты | ImGui-редактор | CSV/PNG-экспорт, снапшоты состояния |
| Порт старого кода | `GameObject`, `Collider`, `UIElement`, анимации | почти ничего не тащим (см. §5) |

### Что это даёт хорошего

Твой главный источник сложности — дескрипторы, атласы, шрифты, пайплайн под спрайты — **на симуляциях откладывается**.
До первой осмысленной картинки тебе нужны: swapchain → render pass → пайплайн с одной вершинной раскладкой →
vertex/instance buffer → **push constants с ортопроекцией**. Всё. Ни одного дескриптора, ни одной текстуры,
ни одного sampler. Это радикально короче пути.

И главное: `VulkanPhysicalDeviceSelector`, который ты уже написал, **остаётся ровно тем же самым**. Смена фокуса
не выбрасывает работу.

## 2. Общий план Vulkan-ядра (одинаков для любой симуляции)

### Этап 0. Отладка (1 вечер, не пропускать)

1. `sudo dnf install vulkan-validation-layers vulkan-tools` → `vulkaninfo --summary`.
   У тебя слоёв нет вообще. Пока кадр не рисуется с нулём ошибок валидации — дальше не идти.
2. `Debug`-логгер с уровнями. В Vulkan `Console.WriteLine` недостаточно.
3. Закоммить текущий каркас на ветку — рабочее дерево сейчас несохранённое.

**Блокер:** проект не собирается. `Application.cs(65,33)`: не виден `VulkanContext` — нужен
`using Engine.Graphic.Vulkan;`. Проверено на копии: после этой строки сборка проходит, 0 ошибок.

### Этап 1. До первого кадра (это ядро, оно не меняется)

1. `VulkanInstance` — `Vk.CreateInstance`, surface-расширения от окна, validation + debug messenger.
2. `VulkanContext` — instance → surface → device → очереди (вход: `SelectedPhysicalDevice`).
3. `VulkanSwapchain` — формат, present mode, extent с clamp, image views, recreate на ресайз.
4. Render pass (один аттачмент, clear), framebuffers.
5. Command pool + 2 кадра в полёте, семофоры + fence, корректная обработка `OutOfDate`/`Suboptimal`.
6. Пайплайн без вершин → **M1: окно с цветом, ресайз без крашей.**

### Этап 2. Первый объект: точка

1. Vertex shader GLSL 450, `layout(push_constant) { mat4 proj; }`, `gl_Position = proj * vec4(pos, 0, 1)`.
2. Вершинный буфер (`HOST_VISIBLE|COHERENT`, замаплен один раз), `VK_PRIMITIVE_TOPOLOGY_POINT_LIST`.
3. Ортопроекция: **левый верхний угол, Y вниз, пиксельные единицы** — как в MonoGame SpriteBatch.
   Зафиксировать конвенцию сразу, иначе потом всё будет перевёрнуто.
4. Blend: для точек/линий — `SrcAlpha / OneMinusSrcAlpha`.

**M2: точка на экране.** Это первый настоящий milestone движка.

Важно про точки: в Vulkan размер точки управляется `gl_PointSize`, но требует фичи `largePoints`, иначе
точка всегда 1 px. Проверь `features.LargePoints` и `limits.PointSizeRange`. **Не строй на точках ничего
серьёзного** — 1 px быстро упирается в предел; точки годятся как отладочный примитив.

### Этап 3. Объекты в количестве: инстансированный квад

1. Базовый квад (4 вершин, 6 индексов) — статический.
2. Instance buffer: `struct Instance2D { Vector2 pos; Vector2 scale; float rotation; uint color; }` ≈ 24 байта.
   Поворот разворачивать в 2×2 в вершинном шейдере — меньше трафика.
3. Камера: pan + zoom (мышь/клавиатура через `Silk.NET.Input`), масштаб и смещение — в push constants.
4. Double buffering: два instance-буфера, пока GPU читает один — CPU пишет другой. Не давать GPU читать
   буфер, который ты в этот момент перезаписываешь.

**M3: 100 000 инстансов кружков/квадратов под 60+ fps.**

### Этап 4. Симуляционный цикл (специфика, которой в игровом движке не было)

1. `FixedStepLoop`: accumulator, `dt_fixed`, ограничение на число шагов за кадр (защита от «спирали смерти»).
2. Интерполяция отрисовки между `state_prev` и `state_curr` по `alpha` — картинка плавная при любом `dt_fixed`.
3. Детерминизм: фиксированный порядок обхода, никаких параллельных сумм с плавающей точкой, фиксированный seed.
   Записать в `sim.log`: seed + число шагов + версия — иначе эксперимент не воспроизводим.
4. **Headless-режим**: `--headless --steps 1000000 --seed 42 --out out.csv` — тот же `Sim.Update`, но без окна и Vulkan.
   Это половина ценности движка для симуляций и главный повод к нему возвращаться.
5. Снапшоты: бинарный save/load состояния → прервать и продолжить. `Time` (у тебя уже есть) → переделать
   под fixed step + clamp `DeltaTime`.

**M4: N=1e5, шаг детерминирован, тот же результат окно vs headless, результат в CSV.**

### Этап 5. Производительность (после того, как работает)

1. Сместить симуляцию на GPU: compute-шейдеры, состояние в SSBO, **вершинный шейдер читает SSBO напрямую
   по `gl_InstanceIndex`** — нулевой трафик CPU→GPU, никаких instance-буферов.
2. Пространственные структуры на CPU для соседей: uniform grid (boids, SPH, коллизии). Sorted by cell —
   и соседей искать по индексам, не перебором O(N²).
3. Дальше: indirect draw, secondary command buffers, tiling.

### Этап 6. Только когда понадобится

* Линии (axes, траектории, векторные поля) — отдельный пайплайн `LINE_LIST`.
* Текст/числа на экране — только через bitmap-атлас, т.е. первый дескриптор + sampler в проекте.
  Отложить максимально.
* Текстуры/картинки.
* ImGui — **не сейчас** (и готового бэкенда под Vulkan в Silk.NET нет, только OpenGL).

## 3. Три архетипа симуляций — от выбора зависит порядок этапов

| Архетип | Примеры | Что нужно сверх ядра |
|---|---|---|
| **A. Агенты / частицы** | boids, n-body, SPH, диффузия частиц, толпа | инстансированные квады, uniform grid для соседей, много объектов |
| **B. Решётки / поля** | Game of Life, реакция-диффузия, волновое уравнение, автоматы | **render-to-texture + ping-pong** (два offscreen-аттачмента), fullscreen quad, блит на экран; либо compute |
| **C. Непрерывные системы / ОДУ** | двойной маятник, логистическая карта, хаос, схемы, орбиты | линии + траектории, фазовая плоскость, небольшие N, вывод графиков |

Ядро (этапы 0–2) у всех трёх одинаковое. Развилка начинается на этапе 3:
A — инстансы; B — отложить инстансы и делать offscreen-аттачменты и ping-pong; C — линии и текст (т.е. раньше всех
упрёшься в дескрипторы — но N маленькое, так что это не проблема).

**Если хочешь, чтобы проект заставлял к себе возвращаться** — бери A или B: там есть что крутить
(масштаб, параметры, N) и на что смотреть ночью в headless-прогоне.

## 4. Ловушки, специфичные именно для симуляций

* **Точность координат.** Симуляции живут на огромных диапазонах (1e-6…1e9). `float` ломается после ~1e7.
  Решение: состояние считать в `double`, а при отрисовке вычитать позицию камеры и передавать в шейдер
  уже `float`-разницу (**camera-relative rendering**). Иначе объекты начнут дёргаться и слипаться.
* **`dt` не равен кадру.** Не путать `Time.DeltaTime` (кадр) и шаг симуляции. Два разных счётчика времени.
* **Детерминизм ≠ автоматически.** Порядок суммирования, `Parallel.For` и зависимость от частоты кадров убивают
  воспроизводимость. Если эксперимент надо повторять — фиксируй всё это и логируй.
* **Проверка рендера без симуляции.** Сделай «renderer test scene»: сетка точек, единичные квады, известные
  координаты. Дёшево ловит регрессии после каждого рефакторинга пайплайна.
* **Камера-наблюдатель.** Мышь pan/zoom — не «фича», а основной инструмент работы с симуляцией.
* **Экспорт.** PNG кадра (readback framebuffer → ImageSharp, который уже в зависимостях) и CSV состояния.
  Для headless-режима без GPU — можно писать PNG прямо из CPU.

## 5. Что убрать из проекта прямо сейчас

* `ImGui.NET` из `2D-Engine-Base.csproj` — не нужен (и `imgui.ini` тоже).
* `Content.mgcb`, `.config/dotnet-tools.json`, `Content/bin/*.xnb`, `Font.spritefont`, `GradientEffect.fx` —
  наследие MonoGame, Vulkan это не читает.
* Старый игровой слой из git-истории (`GameObject`, `Collider`, `PhysicalBody`, `EntitiesAnimations`,
  `UIController`, `UIElement`) — **не тащить**. Держать как справочник, не как основу.
* Из старого имеет смысл взять только идеи: `Camera`, ортопроекция, `Time`, `InputHelper` (и то переписав
  под минимум: pan/zoom/pause/step/reset).
* `SixLabors.ImageSharp 2.1.13` — есть уязвимости, поднять до 3.x. Из неё останется только экспорт PNG.

### Структура

```
src/
  Sim.Core/        // состояние, шаг, детерминизм, сетки соседей, экспорт CSV
  Render/          // абстракция: IRenderer2D (Points/Lines/Instances), Camera, RenderPacket
  Render.Vulkan/   // VulkanInstance, VulkanContext, VulkanSwapchain, пайплайны, буферы
  Sim.*/           // конкретные симуляции (Boids, NBody, ...)
  App/             // окно, ввод, режим headless, CLI
```

Ключевое правило: **симуляция не знает про Vulkan**. Она отдаёт `RenderPacket` (SoA-массивы), рендер его
рисует. Из этого бесплатно получается headless-режим и тестируемость.

## 6. Три следующих шага

1. `sudo dnf install vulkan-validation-layers vulkan-tools`; включить `VK_LAYER_KHRONOS_validation`
   и debug messenger.
2. Создать `VulkanInstance` и заполнить `VulkanContext` (instance → surface → device → очереди,
   используя готовый `VulkanPhysicalDeviceSelector`).
3. `VulkanSwapchain` (формат/present/extent/imageCount + image views + recreate на ресайз).

Дальше: render pass → пайплайн точек → **M2: первая точка**. Это уже настоящий, а не бумажный этап.
